# 공통 인계·단계 확정·실행 프로토콜

[중국어 안내](common-contract.md)｜[한국어 안내](common-contract.ko-KR.md)

프로토콜 버전: 0.6.0. 각 Skill은 이 문서와 `novice-guidance-protocol.md`의 내용이 한 글자도 다르지 않은 복사본을 포함합니다. 배포 시 일치 여부를 검증하며 특정 컴퓨터의 공용 디렉터리에 의존하지 않습니다.

## 0. 작업 깊이와 전문 프로토콜의 적용 범위

`interaction_mode`는 대화 계층 개념이며 공통 YAML에는 넣지 않습니다. 초보자·협업·전문가 대화 모드는 `novice-guidance-protocol.md`를 참고합니다. 어떤 대화 모드에서도 다음 작업 깊이를 구분해야 합니다.

- **논의**: 현재 질문에 직접 답하고 구체적인 판단이나 부분 시험 원고를 제공합니다. 불확실하거나 결론을 내리지 않아도 되며 전체 공통 헤더, 후보 상태, 잠긴 마스터, 제작 테스트, 파일 저장을 요구하지 않습니다.
- **탐색 초안**: 교체 가능한 가정, 연동 후보, 비교를 허용합니다. 임시임을 명확히 표시하며 승인본이나 정식 candidate처럼 취급하지 않습니다.
- **정식 원고**: 사용자가 지정한 범위만 완전하게 제공합니다. 입력이 충분하면 바로 작성하며 계속 질문하는 것으로 창작을 대신하지 않습니다. 정식 원고도 사용자가 확정해야 confirmed가 됩니다.
- **제작 인계·검증**: 관리되는 산출물, 외부 실행, 상위 버전 변경, 증거 검토 단계에서는 이 문서의 공통 헤더, 권한, 증거, 의존성 게이트를 모두 적용합니다.

공통 순환은 `현재 의도 → 직접 판단·구체적 시험 작성 → 필요한 경우 소수 대안과 비용 → 피드백 반영 → 영향받은 항목만 수정`입니다. 권한 규칙과 실행 진행은 분리합니다. 논의 중 파일을 저장하지 않는다고 해서 대화 안에서 유용한 초안을 만들 수 없는 것은 아닙니다.

## 1. 공통 헤더와 도메인 내용 분리

제작 인계·검증 및 등록을 명확히 요구한 정식 산출물은 공통 헤더로 시작하고 구체적인 디자인과 표는 payload에 둡니다. 논의, 탐색, 읽기용 부분 원고에는 공통 헤더를 강제하지 않습니다.

```yaml
artifact_id: ART-example
version: v1
artifact_type: idea
creative_mode: narrative
subject_type: character-led
lifecycle_status: draft
production_status: not_applicable
approval_level: none
upstream_versions: {}
confirmed_evidence: []
open_questions: []
recheck_trigger: []
next_action: request_review
payload: {}
```

- `artifact_id`: 논리 산출물의 안정적인 ID이며 버전을 포함하지 않습니다. `version`은 별도로 증가합니다. Skill 버전은 산출물 버전이 아닙니다.
- `artifact_type`: idea / script / world / character / scene / storyboard / prompt / clip / review.
- `creative_mode`: narrative / perceptual / conceptual. 모드 변경은 창작 변경이며 하위 단계가 임의로 전환할 수 없습니다.
- `subject_type`: character-led / environment-led / object-led / abstract. 인물이 없으면 `payload.character`는 null이며 인물 필드는 “해당 없음”으로 표시합니다.
- `lifecycle_status`: draft / candidate / confirmed / needs_recheck / invalidated.
- `production_status`: not_applicable / not_started / planned / awaiting_external_generation / submitted / generated / under_review / reviewed / failed.
- `approval_level`: none / direction_approved / production_approved / human_confirmed.
- `upstream_versions`: 안정적인 ID에서 명확한 버전으로의 매핑이며 “최신 버전”이라고 쓰지 않습니다.
- `confirmed_evidence`: 실제 사람의 선택 또는 검증 근거입니다. 없으면 비워 두며 꾸며 내지 않습니다.
- `open_questions`, `recheck_trigger`, `next_action`: 각각 미결 질문, 재검토 조건, 다음 동작을 기록합니다.

### 알 수 없는 입력과 부분 검토

모드, 대상, 원본 기록, 버전이 제공되지 않으면 추측하지 않습니다. `draft` 또는 `needs_recheck` 진단 기록에서 null을 명시하고 `payload.record_completeness`를 `incomplete`, `open_questions`에 누락 항목, `approval_level`을 `none`으로 둘 수 있습니다. 이는 유효한 접수·진단 기록이지 정식 제작 인계 승인이 아닙니다. 정식 candidate/confirmed 또는 제작 제출 전에 적용 가능한 enum과 의존 버전을 완성합니다. 원본 기록이 없으면 차이 패치·영향 보고서를 제공하며 전체 이전 헤더를 꾸며 내지 않습니다.

## 2. 상태와 사람의 판단은 서로 대신할 수 없습니다

방향 확정은 제작 마스터 승인이 아니며, 프롬프트 승인은 요청 제출이 아니며, 반환 파일은 리뷰 통과가 아니며, 기계 통과는 사람의 승인이 아니며, 부분적인 사람의 승인은 전체 Canon 편입이 아니며, 파일 저장은 내용 확정이 아닙니다.

정식 후보는 공통 프로토콜 요구를 만족해야 합니다. 탐색 중 방향, 부분 시험 원고, 입력이 부족한 내용은 여전히 초안입니다. 현재 후보를 거절하면 candidate 상태로 거절 이유를 기록하거나 새 버전을 만들 수 있으며, 명확히 더 이상 사용하지 않을 때만 invalidated로 둡니다. 리뷰 기록 자체의 confirmed는 보고서가 확정되었음을 나타낼 수 있지만 평가 대상의 상태를 바꾸지는 않습니다.

생성 도구가 없으면 `awaiting_external_generation`으로 둘 수 있고 실제 결과 필드는 null입니다. 검증 가능한 제출 증빙이 있어야 submitted, 접근 가능한 반환 파일·결과 ID가 있어야 generated입니다. 텍스트 디자인의 production_status는 보통 `not_applicable`입니다.

사람의 판단은 최소한 pending / accept / reject / partial-absorb / return을 허용합니다. 아직 답하지 않았다면 pending이며 Agent가 대신 승인할 수 없습니다.

## 3. 단계 완료 게이트

`confirmed`는 단계 수준의 사실이며 말투를 보고 추측하지 않습니다. 다음 조건을 모두 충족해야 confirmed로 표시할 수 있습니다.

1. **대상이 명확함**: 확정하는 단계, 산출물 ID, 버전, 범위를 밝힙니다. 부분 확정을 전체 프로젝트 확정으로 확대하지 않습니다.
2. **전체 산출물이 제시됨**: 사용자가 저장할 전체 본문 또는 명확히 찾을 수 있는 전체 파일을 보았으며 요약만 본 것이 아닙니다.
3. **단계 확정이 명확함**: 사용자가 “이 버전 확정 / 이 단계 완료 / 이대로 최종 확정 / 이 단계 잠금”이라는 의미를 명확히 표현합니다. Agent 추천, 침묵, 다음 단계 진행, “좋아요 / 괜찮아요 / 방향이 맞아요 / 한번 볼게요 / 거의 됐어요” 같은 긍정적 피드백은 포함되지 않습니다.
4. **저장 권한이 유효함**: 이번에 명확히 권한을 주었거나 프로젝트 수준 지속 저장 권한이 있고 이 단계도 명확히 확정되었습니다.
5. **의존성과 미결 항목이 보임**: 상위 버전이 명확합니다. 진행을 막지 않는 불확실성은 남길 수 있지만 숨기거나 꾸며 내지 않습니다.

모호하면 “계속 수정할까요, 아니면 이 단계를 확정하고 기존 권한에 따라 저장할까요?”처럼 짧은 질문 하나만 합니다. 답변 전에는 draft/candidate를 유지합니다.

프로젝트 수준 지속 권한은 반복 질문만 줄이며 **각 단계의 내용 확정을 절대 대신할 수 없습니다**. 지속 권한을 철회하면 이후 저장은 매번 다시 묻습니다. 철회해도 과거 파일은 삭제하지 않습니다.

## 4. 로컬 Markdown 저장 필수 규칙

### 4.1 저장 허용 조건

- `confirmed`: 단계 완료 게이트를 통과하고 유효한 단계 확정 저장 권한이 있어야 confirmed 산출물을 쓸 수 있습니다.
- `draft` / `candidate`: 사용자가 초안이나 후보 저장을 명확히 요구한 경우에만 저장합니다. 파일명과 본문에서 상태를 분명히 표시하며 확정본처럼 보여서는 안 됩니다.
- 권한이 없으면 대화에서 전체 내용을 제공할 수 있지만 임의로 파일을 쓰지 않습니다.

### 4.2 전체 산출물 저장

사용자가 보고 확정한 **전체 단계 산출물**을 저장합니다. 적용되는 본문, 핵심 표, 공통 헤더, 미결 항목, 인계 정보를 포함합니다. 요약, 대화 기록, 링크 목록, “대화 참고”만 저장하지 않습니다. 내용이 길어 여러 파일로 나누면 인덱스에 모든 구성 파일을 기록하고 하나의 버전으로 취급합니다.

### 4.3 버전과 덮어쓰기

- 새 버전에는 새 파일명 또는 새 버전 디렉터리를 사용하며 기본적으로 기존 버전을 **덮어쓰지 않습니다**.
- `artifact_id`는 안정적으로 유지하고 `version`은 증가시킵니다. 권장 파일명은 `<단계 또는 산출물>-<버전>-<상태>.md`입니다.
- 과거 파일의 덮어쓰기, 삭제, 이동은 별도의 고위험 동작이며 대상 파일에 대한 명확한 권한이 필요합니다. 프로젝트 수준의 “단계 확정 후 지속 저장”에는 덮어쓰기 권한이 없습니다.
- 상위 버전이 바뀌면 이전 산출물과 승인 이력을 보존하며 이전 confirmed 내용을 조용히 다시 쓰지 않습니다.

### 4.4 최초 저장 시 프로젝트 자동 초기화

프로젝트 디렉터리가 명확하고 사용자가 이번 저장 권한 또는 유효한 지속 저장 권한을 제공하면 Agent가 프로젝트 기본 기록을 확인합니다. `PROJECT_BRIEF.md`, `AUTHORIZATIONS.md`, `PROJECT_INDEX.md`, `SESSION_HANDOFF.md`, `DECISIONS.md`가 누락되었으면 패키지의 `templates/`에서 자동 생성하고 확인된 최소 정보를 기록하며 모르는 내용은 “알 수 없음/없음”으로 유지한 뒤 다시 읽어 검증합니다. 초보자에게 템플릿 복사, Skill 선택, 내부 상태 필드 입력을 요구하지 않습니다.

자동 초기화는 로컬 저장 트랜잭션의 일부이며 버전, 권한, 인덱스, 인계, 결정 추적을 지원하는 기본 파일만 만듭니다. `stage-deliverable-template.md`는 Agent 내부 참고용이며 사용자 프로젝트에 복사하지 않습니다. 템플릿을 읽을 수 없으면 의미가 같은 최소 구조를 만들 수 있지만 실제 출처와 생성 결과를 알려야 하며 읽지 않은 템플릿을 사용했다고 말해서는 안 됩니다.

`AUTHORIZATIONS.md`를 초기화할 때는 사용자가 현재 대화에서 명확히 제공한 권한의 원래 의미, 범위, 유효 기간만 기록합니다. 승인되지 않은 항목은 denied를 유지합니다. 자동 초기화는 덮어쓰기, 삭제, 업로드, 결제, 생성, 게시, 평가, 학습, 연구 권한을 만들지 않습니다. 기존 기본 파일을 빈 템플릿으로 덮어쓰지 않으며 내용이 충돌하면 원본을 보존하고 재검토로 표시합니다.

### 4.5 쓰기 후 검증과 등록

매번 저장할 때 다음을 완료해야 합니다. 최초 저장에는 앞의 기본 파일 초기화와 다시 읽기도 포함됩니다.

1. 대상 파일 쓰기
2. 대상 파일을 다시 읽어 경로, 버전, 상태, 본문 완전성, 핵심 단락 확인. 필요한 경우 구조 또는 해시 검사
3. `PROJECT_INDEX.md` 업데이트: 산출물, 버전, 상태, 경로, 상위 의존성, 확정 근거 등록
4. `SESSION_HANDOFF.md` 업데이트: 마지막 완료 단계, 현재 유효 버전, 미결 질문, 다음 작은 단계 기록
5. 권한이 바뀌면 `AUTHORIZATIONS.md`, 결정이 바뀌면 `DECISIONS.md` 업데이트
6. 업데이트한 파일을 다시 읽어 상호 참조가 존재하고 일치하는지 확인

쓰기 또는 검증 중 하나라도 실패하면 실패 지점과 여전히 신뢰할 수 있는 상태를 그대로 보고해야 하며 **“저장 완료 / 업데이트 완료 / 파일 기록 완료”라고 말해서는 안 됩니다**. 일부만 썼다면 partial로 표시하고 인덱스를 confirmed로 올리지 않습니다.

### 4.6 저장은 다른 권한이 아닙니다

작품 저장은 기존 파일 덮어쓰기, 소재 업로드, 외부 서비스 호출, 비용 발생, 공개 게시, 학습·분석, 연구 데이터 수집, 연구 참여 동의가 아닙니다. 각 항목은 별도 권한이 필요합니다. 특히 **작품 저장은 절대 연구 동의가 아닙니다**. 연구는 기본적으로 denied이며 별도로 명확하고 철회 가능하게 활성화해야 합니다.

## 5. 권한과 외부 실행 경계

권한은 최소한 단계 확정 후 로컬 새 버전 저장, draft/candidate 저장, 덮어쓰기·삭제, 업로드, 결제·자원 소비, 공개 게시, 연구 데이터 동의로 나눕니다. 한 권한에서 다른 권한을 추론하지 않습니다.

사용자가 준비만 승인하고 제출은 승인하지 않았다면 산출물은 planned, `next_action=await_user_authorization`으로 둘 수 있습니다. 사용자 또는 외부 도구가 실행할 것이 명확하고 인계 준비가 완료된 경우에만 awaiting_external_generation으로 둘 수 있습니다. 어느 상태에서도 임의 업로드·결제를 하거나 제출했다고 말할 수 없습니다. 파일 존재는 원격 접근 가능성을 뜻하지 않으며 소재 목록은 업로드 증거가 아닙니다.

프로젝트를 처음 명확히 승인할 때 “각 단계를 명확히 확정한 뒤 기존 버전을 덮어쓰지 않는 새 버전을 자동 저장”하는 지속 권한을 제안할 수 있습니다. 지속 권한의 범위, 활성화 근거, 철회 상태를 `AUTHORIZATIONS.md`에 기록해야 합니다. 기록이 없거나 의미가 불명확하면 미승인으로 취급합니다.

## 6. 세션 간 복구 프로토콜

새 세션에서는 대화 기억으로 추측하지 않고 다음 순서로 복구합니다.

1. 프로젝트 루트 디렉터리를 찾고 `PROJECT_BRIEF.md`가 있으면 읽습니다.
2. `AUTHORIZATIONS.md`를 읽어 현재 실행 가능한 경계를 확인합니다. 연구 권한이 없으면 항상 denied로 취급합니다.
3. `PROJECT_INDEX.md`를 읽어 현재 confirmed, candidate, draft와 명확한 버전을 찾습니다.
4. `SESSION_HANDOFF.md`를 읽어 이전 세션의 중단 지점, 미결 질문, 다음 작은 단계를 파악합니다.
5. 인덱스에 따라 현재 유효 산출물 파일을 다시 읽습니다. 인덱스만 있고 파일이 없으면 confirmed 상태를 인정하지 않습니다.
6. 필요한 경우 `DECISIONS.md`를 읽어 사용자의 명확한 결정과 거절한 방향을 확인합니다.
7. 사용자에게 쉬운 말로 “어디까지 확정되었는지, 현재 후보가 무엇인지, 이번 대화에서 제안하는 작은 목표가 무엇인지” 설명합니다. 복구 자체는 새로운 확정을 만들지 않습니다.

실제 산출물 파일, 명확한 확정 근거, 인덱스, 인계 기록은 서로 일치해야 합니다. 충돌하면 원본 파일을 보존하고 `needs_recheck`로 표시한 뒤 사용자에게 충돌을 설명합니다. 편리한 항목 하나를 사실처럼 선택하지 않습니다. 연구 계층 기록은 production의 확정 상태를 역으로 수정할 수 없습니다.

## 7. 상위 버전 변경과 전파 재검토

이전 산출물과 승인 이력을 보존하고 실제 변경 필드를 기록합니다. `upstream_versions`를 따라 직접·간접 소비자를 추적하며 정체성, 공간, 규칙, 동작, 시간, 소리, 인터페이스 영향을 검사합니다. 영향을 받은 대상은 `needs_recheck`, 현재 `approval_level`은 none으로 바꾸고 이전 승인은 `payload.approval_history`로 옮깁니다. 과거 생성 사실은 그대로 유지하지만 현재 승인 버전으로 사용하지 않습니다. 알 수 없는 영향도 우선 재검토하며 관련 없는 항목은 검사 이유를 기록합니다. 재검토 후 실제 버전, 증거, 승인을 업데이트하고 필요할 때만 다시 생성합니다. 모든 항목을 무조건 다시 만들지 않습니다.

## 8. 모드, 증거, 수정

- narrative는 목표·저항·선택·결과를 사용하지만 구체적인 갈등 모델은 적합할 때만 적용합니다.
- perceptual은 지각 목표·소재 공간 제약·관람 변화·완료 기준을 사용합니다.
- conceptual은 명제·대조 조작·관찰 지표·반례·해석 한계를 사용합니다.
- 기준선은 프로젝트에서 확정하며 흑백, 손상, 무인, 유인, 추상일 수 있습니다. 정상 컬러로 자동 복원하지 않습니다.
- 플랫폼 기능을 모르면 검증할 항목으로 기록하며 예시만 보고 길이, 참조 수, 오디오, 시작·종료 프레임 기능을 추론하지 않습니다.
- 이미지는 동작과 오디오 트랙을 증명하지 못하고, 샘플 프레임은 전체 구간 연속성을 증명하지 못하며, 결과가 없으면 결과를 평가하지 않습니다.
- 기본적으로 주요 변수 하나를 비교합니다. 실제로 결합된 문제라면 여러 항목을 함께 수정할 수 있지만 단일 변수의 원인이라고 주장할 수 없음을 밝힙니다. 참조 파일 존재, 정적 검증 통과, Agent 실행은 실제 생성이나 사람의 확정 증거가 아닙니다.

우선순위: 진실성과 사용자 권한은 하위 규칙으로 덮어쓸 수 없습니다. 공통 본문은 기본 범위를 정합니다. reference는 조건이 충족될 때만 사용합니다. 프로젝트에서 명확히 확정한 내용은 창작 스타일, 길이, 배치 등의 기본값을 바꿀 수 있습니다. 충돌이 불명확하면 충돌을 기록하고 영향을 받은 단계를 중단합니다.

## 9. 최종 납품 게이트

공통 헤더가 완전하고, 의존성이 명확하고, 모드가 변질되지 않고, 증거가 실제이며, 미결 항목이 보이고, 생성 진행과 승인이 분리되고, 이전 버전 영향이 처리되고, 다음 단계가 명확해야 합니다. 저장 완료를 주장하려면 유효한 권한, 명확한 단계 확정, 완전한 새 버전 파일, 성공적인 다시 읽기, `PROJECT_INDEX.md`와 `SESSION_HANDOFF.md`의 동기화·재확인도 있어야 합니다. 논의와 부분 원고는 적용되는 항목만 검사하며 필드를 채우기 위해 승인, 증거, 마스터, 제작 테스트를 꾸며 내지 않습니다.
